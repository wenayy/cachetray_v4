1 · How the animations actually work

Every concept, in plain English, with your real code — and live demos you can replay.

THE BIG IDEA

There is no video, no GIF, no library. Everything is the real UI (HTML/CSS) manipulated by JavaScript in real time. Think of a puppet show: HTML is the puppet, CSS is its joints (how it can move), JavaScript is the puppeteer (when to pull each string). The key insight: JS rarely draws the animation — it changes one value and the browser draws the in-between frames.

"The demos aren't recordings — they're the real UI. A JavaScript 'director' plays a script: it moves a fake cursor, toggles CSS classes, and lets CSS transitions do the actual motion. It's the same DOM the real product renders; I just automated the user's hand."

① CSS transitions — the foundation

THE IDEA

A transition says: "when this property changes, don't jump — glide to the new value over some time." You don't write a loop or calculate frames. You mark a property animatable, change it once, and the browser animates it — on the GPU, without blocking your JS. Like a soft-close door: you just push it, the hinge handles the smooth close.

cachetraywebsite/index.html:1060 — the fake cursor 
/* "if left or top changes, glide there over 0.55s" */
.demo-cursor {
  transition: left 0.55s cubic-bezier(0.4,0,0.2,1),
              top  0.55s cubic-bezier(0.4,0,0.2,1);
}

Two terms to know: cubic-bezier(...) is easing — the "personality" of the motion. linear looks robotic; easing makes things start slow, speed up, ease to a stop, like real objects with weight. And transform is cheaper than top/left because it doesn't trigger a layout reflow — that's why the scroll reveals use transform: translateY().

"I lean on CSS transitions instead of animating in JavaScript. I change one value and the browser interpolates every frame on the compositor — less code, smoother, and it doesn't block the main thread. The cubic-bezier easing is what makes motion feel human instead of robotic."

index.html:2513 — find a target's center, relative to the demo box 
function elCenterRelative(el, container) {
  const eR = el.getBoundingClientRect();        // target's box on screen
  const cR = container.getBoundingClientRect(); // demo box on screen
  return {
    x: eR.left - cR.left + eR.width/2,   // center X, INSIDE the container
    y: eR.top  - cR.top  + eR.height/2
  };
}

Why subtract the container's position? getBoundingClientRect() gives coordinates relative to the whole window, but the cursor lives inside the demo box. Subtracting the container's corner converts "position on screen" → "position inside this box." That's what makes it land dead-center on any screen size.

③ async/await — sequencing like a screenplay

THE IDEA

An animation is a sequence: move, wait, click, wait, reveal. With raw setTimeout callbacks you get "callback hell" — functions nested in functions. async/await lets you write the steps top-to-bottom like a recipe, even with pauses between them.

index.html:2345 — the whole timing system is this one function 
function w(ms){ return new Promise(r => setTimeout(r, ms)); }
// now `await w(500)` = "pause this function 500ms, then continue"
index.html:2606 — read it like stage directions 
async function animFav1() {
  if(fav1Running) return;              // lock (see below)
  fav1Running = true;
  await moveCursorToEl(cur, item1);    // glide to the item
  acts1.style.opacity = '1';         // reveal buttons
  await moveCursorToEl(cur, starBtn);   // glide to the star
  await clickCursor(cur);             // click!
  badge.style.opacity = '1';         // it's favourited
  await hideCursor(cur);              // fade cursor out
}
CLASSIC INTERVIEW LADDERExplain async/await by climbing: 1) Callbacks (pass a fn to run later; nesting = hell) → 2) Promises (an object for a future value; .then() chains flatter) → 3) async/await (sugar over Promises; await pauses until it resolves, so async reads like sync).

"Each step returns a Promise wrapping a setTimeout, so I can await it. That turns deeply nested callbacks into a flat, top-to-bottom sequence that reads like a screenplay — move, wait, click, reveal, hide."

④ IntersectionObserver — reveal on scroll

THE IDEA

The naive way to "animate when scrolled into view" is a scroll listener measuring every element on every tick — hundreds of times a second, janky. IntersectionObserver flips it: the browser tells you when an element enters the viewport, efficiently.

▶ Live demo — scroll this box

↓ keep scrolling…

✨ I faded up the moment I entered view — triggered by IntersectionObserver, animated by a CSS transition.
index.html:2485 
const observer = new IntersectionObserver((entries) => {
  entries.forEach(e => {
    if(e.isIntersecting){
      e.target.classList.add('visible');  // → CSS fades it up
      observer.unobserve(e.target);        // reveal once, then stop watching
    }
  });
}, { threshold: 0.1 });                    // fire at 10% visible

Two craft details: threshold:0.1 waits until 10% is visible (natural moment), and unobserve stops watching after firing — no wasted work. That cleanup separates "works" from "works well."

"For scroll reveals I use IntersectionObserver, not a scroll listener. The browser notifies me when an element enters the viewport — no per-frame polling — and I unobserve after firing once. JS just adds a class; CSS does the fade."

⑤ The re-entrancy guard (a lock)

THE IDEA

The demos loop and can be re-triggered by tab switching. If an animation starts again while still running, two copies fight over the same DOM. A boolean "lock" prevents it.

let fav1Running = false;
async function animFav1() {
  if(fav1Running) return;   // already running? bail.
  fav1Running = true;       // claim the lock
  // …animate…
  fav1Running = false;      // release at the end
}

"Each demo has a boolean re-entrancy guard — a lock. It's the same idea as a mutex: only one instance mutates the DOM at a time, so I never get two animations fighting over the same elements."

⑥ Bonus flex: double requestAnimationFrame

THE IDEA

The undo bar counts down over 3.5s. If you set width to 100% then instantly 0%, the browser batches both and you see no animation. You must force a paint of the 100% state first.

index.html:2787 
undoFill.style.transition = 'none'; undoFill.style.width = '100%'; // snap full
requestAnimationFrame(() => requestAnimationFrame(() => {
  undoFill.style.transition = 'width 3.5s linear';
  undoFill.style.width = '0%';                        // now animate down
}));

Waiting two frames guarantees the browser painted the 100% state, so the transition has a starting frame. This is "forcing a reflow between two style changes."

"For the undo countdown I set width to 100% with no transition, then wait two animation frames before transitioning to 0% — forcing the browser to paint the full state first, otherwise it batches both writes and you see nothing."

Why no framework? (know this cold)

"It's a static marketing site — no shared state, no routing, no data fetching. React would add a build step, a bundler, ~40KB of runtime plus hydration, for zero benefit. Vanilla with CSS transitions loads instantly and animations run on the compositor. I match the tool to the problem — knowing when not to add a framework matters as much as knowing how to use one."

0 · Animation basics — in plain words

You said you know nothing about this — perfect, start here. By the end you'll know the ~7 properties behind every animation on the web, and you'll have pressed "play" on each one.

THE ONE SENTENCE THAT EXPLAINS ALL ANIMATION

You change a property (like position or opacity), and transition tells the browser to slide to the new value smoothly instead of jumping. That's the whole trick. Everything below is just which property you change.

1 · transition — the "make it smooth" switch

What it is: the master instruction. It says "when something about this element changes, animate the change instead of snapping to it."

What it does: without it, every change is instant. With it, changes glide. No transition = no animation. This is the single most important word — memorize it.

How to write it: transition: WHAT · HOW-LONG · FEEL

.box {
  transition: all 0.4s ease;
  /*         ↑    ↑     ↑                */
  /*      WHAT  HOW-LONG  FEEL            */
  /* "all" = animate any property that changes */
}

It glides because the box has transition. Delete that one line and it would teleport instantly. Click again to send it back.

2 · transform — move, resize, or spin (without breaking the page)

What it is: the property you change to visually move/scale/rotate an element. It has three everyday flavours:

  • translateX(40px) / translateY(-30px) — slide sideways / up-down.
  • scale(1.3) — grow (1 = normal, 1.3 = 30% bigger, 0.8 = smaller).
  • rotate(45deg) — spin by an angle.

Why transform and not top/left/width? Because transform is GPU-fast and doesn't shove other elements around (no layout "reflow"). This is the pro habit: animate with transform and opacity whenever you can.

Same property (transform), three effects. Click again to reverse.

3 · opacity — fade in and out

What it is: how see-through something is. 1 = fully visible, 0 = invisible, 0.5 = half. Change it (with a transition) and you get a fade.

The classic combo: opacity + translateY together = the "fade up" effect you see everywhere (and on your own site's scroll reveals).

Goes see-through smoothly. Click again to fade back in.

4 · Duration — how long it takes

What it is: the time value in the transition (the 0.4s part). Small = snappy, big = slow and dramatic.

ValueFeels likeUse for
0.15sInstant, snappyButtons, hovers, small UI
0.3–0.5sSmooth, naturalMost things (the sweet spot)
0.8s+Slow, dramaticBig hero reveals

Same distance, different duration. Same box moves back on a second click.

5 · Easing — the "feel" or personality of the motion

What it is: the last part of the transition. It controls the speed curve — does it move at a constant rate, or speed up and slow down like a real object?

  • linear — constant speed. Looks robotic. (Good only for spinners.)
  • ease / ease-in-out — starts slow, speeds up, eases to a stop. Looks natural.
  • cubic-bezier(0.34,1.56,0.64,1) — a custom curve that overshoots and springs back. Feels alive/bouncy.

Top = linear (robotic). Bottom = spring cubic-bezier (bounces at the end). Watch how different the same move feels.

DON'T MEMORIZE CUBIC-BEZIER NUMBERSNobody remembers those four numbers. You copy a curve you like from a site like easings.net or cubic-bezier.com. Just know what easing is for: making motion feel human.

6 · Delay — wait before starting (how "stagger" works)

What it is: tell an element to wait a moment before it animates. Give each item in a list a slightly bigger delay and they animate in one-after-another — that pleasing "cascade" effect.

.item:nth-child(1){ transition-delay: 0s; }
.item:nth-child(2){ transition-delay: 0.1s; }
.item:nth-child(3){ transition-delay: 0.2s; }  /* → staggered cascade */

They lift one after another because each has a bigger delay. Click again to drop them.

7 · @keyframes + animation — for looping / multi-step motion

The difference from transition:

  • transition = animate from A to B when something changes (needs a trigger, like a click or a class).
  • animation + @keyframes = a defined timeline that runs on its own, and can loop forever (pulses, floating, spinners — no trigger needed).
/* Step 1: define the timeline */
@keyframes float {
  0%, 100% { transform: translateY(0); }   /* start & end */
  50%       { transform: translateY(-20px); } /* middle */
}
/* Step 2: play it, forever */
.box { animation: float 2s ease-in-out infinite; }

These loop on their own — no click needed to keep going. Click the same button again to stop.

THE RECIPE FOR 90% OF WEB ANIMATIONS

Set a resting state (opacity:0; transform:translateY(20px)), add a transition, then change to the active state (opacity:1; transform:translateY(0)) — with JavaScript toggling a class at the right moment. That "fade up" pattern is literally what your whole site's scroll reveals do.

Vanilla vs React vs Tailwind vs Next

The confidence-builder: the animation is identical in every stack. Frameworks don't replace CSS — they just repackage it.

THE KEY INSIGHT

The browser only understands HTML, CSS, and JavaScript. React, Tailwind, and Next all compile down to those three. So the concepts you learned aren't "vanilla concepts" — they're THE concepts, and they transfer 1:1 to every framework.

              What you WRITE          What the browser RUNS
  Vanilla  →  HTML/CSS/JS         →   HTML/CSS/JS
  React    →  JSX + state         →   HTML/CSS/JS   (compiled)
  Tailwind →  utility classes     →   CSS           (compiled)
  Next.js  →  React + routing     →   HTML/CSS/JS   (compiled)

3 · Clean-code refactor

Learn to write code interviewers respect. We take a messy version of a real demo and clean it up — with the "why" behind every change.

THE PRINCIPLE

Clean code isn't about clever tricks — it's about reducing what the next reader has to hold in their head. Good names, no repetition, small functions, and consistent patterns. Below, the same behaviour written two ways.

❌ Before (works, but messy)
✅ After (clean)
// Repetitive, magic numbers, unclear names, no reuse
function go() {
  var c = document.getElementById('cur');
  var b = document.getElementById('btn');
  c.style.left = b.getBoundingClientRect().left - 300 + 'px';
  c.style.top  = b.getBoundingClientRect().top - 120 + 'px';
  setTimeout(function(){
    c.classList.add('clicking');
    setTimeout(function(){
      c.classList.remove('clicking');
      b.style.background = 'yellow';
      setTimeout(function(){ b.style.background = ''; }, 2000);
    }, 150);
  }, 680);
}
// Named constants, helpers reused, flat async flow, clear intent
const GLIDE_MS = 680, CLICK_MS = 150, HIGHLIGHT_MS = 2000;
const wait = ms => new Promise(r => setTimeout(r, ms));

async function clickButtonWithCursor(cursor, button) {
  glideTo(cursor, button);           // position is computed inside the helper
  await wait(GLIDE_MS);
  await pressClick(cursor);            // adds/removes .clicking for CLICK_MS
  highlight(button, HIGHLIGHT_MS);      // one job, clearly named
}

The 5 changes and why each matters

  1. Named constants over magic numbers. GLIDE_MS tells the reader why 680 exists. → "Magic numbers hide intent."
  2. Reusable helpers (wait, glideTo, pressClick) instead of copy-pasting setTimeout. → DRY: Don't Repeat Yourself.
  3. Flat async/await instead of nested callbacks. → Readability; no "callback pyramid."
  4. Descriptive names — clickButtonWithCursor, not go; button, not b. → Code is read 10× more than written.
  5. Single responsibility — each helper does one thing. → Easy to test, reuse, and reason about.

"When I refactor, I optimize for the next reader. I replace magic numbers with named constants, pull repeated logic into small single-responsibility helpers, and flatten async flow with async/await. The behaviour is identical — but the intent is now obvious from the names alone."

4 · Build a new animation from scratch

See the whole process — from empty box to working animation — so you understand how it's made, not just the finished code.

We'll build a "copied to clipboard" toast: click a button, a confirmation slides up, then fades away. It uses every core concept: CSS transitions, class toggling, async/await timing, and a lock.

▶ The finished thing — try it

✓ Copied to clipboard

Step 1 — HTML: the pieces (start with the DOM)

Why first? Animation is just moving DOM. Build the static thing before you move it.

<button onclick="copyToast()">📋 Copy snippet</button>
<div id="toast">✓ Copied to clipboard</div>

Step 2 — CSS: define resting state + how it moves

The key move: the toast rests hidden (pushed down + invisible). The transition declares how it animates when we change those values.

#toast {
  transform: translateY(60px);   // resting: pushed down…
  opacity: 0;                     // …and invisible
  transition: all .4s cubic-bezier(0.34,1.56,0.64,1); // springy easing
}
#toast.show { transform: translateY(0); opacity: 1; } // shown state

That cubic-bezier(0.34,1.56,0.64,1) overshoots past 1 — it gives a little bounce/spring, which feels alive.

Step 3 — JS: the director (toggle the class, then untoggle)

let toastBusy = false;                 // ① the lock
const wait = ms => new Promise(r => setTimeout(r, ms));

async function copyToast() {
  if (toastBusy) return;              // ② don't overlap
  toastBusy = true;
  const t = document.getElementById('toast');
  t.classList.add('show');           // ③ change values → CSS slides it up
  await wait(1800);              // ④ hold it visible
  t.classList.remove('show');        // ⑤ CSS slides it back down
  await wait(400);               // ⑥ let the exit finish
  toastBusy = false;               // ⑦ release the lock
}

Notice: the JS never animates anything. It adds a class, waits, removes it. CSS does all motion. That's the entire philosophy of your site in 12 lines.

YOUR TURN (practice)

Try describing, without looking: (1) why the toast rests in the hidden state, (2) what the show class changes, (3) why we await wait(400) before releasing the lock. If you can, you understand the model — not just the code.

"To build an animation I start with the static DOM, define its resting and active states in CSS with a transition between them, then use JavaScript only to toggle a class at the right moments — sequenced with async/await and protected by a lock. The browser handles all the actual motion."
